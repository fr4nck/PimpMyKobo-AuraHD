## Contre-lecture ciblée : défauts dans le code historique consulté

Ces problèmes sont **observables dans les sources de ce fork** ; ils ne sont **pas tous attribuables à Marek**, certains peuvent être hérités du BSP. Ce sont des risques statiques à tester et corriger avant toute réutilisation, **pas des incidents reproduits sur une liseuse**.

1. **Accès hors bornes possible dans ZForce :** dans [`zforce_i2c.c`](https://github.com/marek-g/kobo-kernel-2.6.35.3-marek/blob/70889a3c6208c94abfab0eb90cfff3ccea3b3579/drivers/input/touchscreen/zforce_i2c.c), `id = ((octet >> 2) & 0x0f) - 1` est utilisé immédiatement pour indexer `x[id]` / `y[id]` / `g_touch_pressed[id]`. Un champ ID de valeur zéro conduirait à `-1` sans validation préalable ; les tailles de trames I²C et le nombre de contacts sont également insuffisamment vérifiés.
2. **Mauvaise vérification d'allocation :** dans [`mxc_epdc_fb.c`](https://github.com/marek-g/kobo-kernel-2.6.35.3-marek/blob/70889a3c6208c94abfab0eb90cfff3ccea3b3579/drivers/video/mxc/mxc_epdc_fb.c), après `_blocksCRC16 = kzalloc(...)`, le code teste **`!_line_ranges` une seconde fois** au lieu de `!_blocksCRC16`. Une allocation CRC échouée ne provoque donc pas le diagnostic attendu et le pointeur reste potentiellement nul.
3. **Gestion des bornes EPDC :** le code réserve `2*native_height` entrées pour les plages, mais teste `no_ranges > native_height` avant insertion, au lieu de `>=`. Les calculs CRC lisent systématiquement **16 pixels × 8 lignes**, avec allocation de `(native_width/16)*(native_height/8)` par **division entière**, sans protection évidente pour des dimensions non multiples ou rotations. Il faut documenter les invariants réels avant toute opération sur un écran HD.
4. **Coût et interaction avec le rendu PMKB :** travail CRC tous les ~100 ms après modification, updates partiels possiblement nombreux, et limitation à **un** buffer EPDC. Aucun benchmark précis de RAM, autonomie, réactivité ou artefacts visuels disponible pour notre écran ; pour la matrice CRC seule, **1440/16 × 1080/8 × 2 = 24 300 octets** si la géométrie native correspond bien à ces dimensions. Ce chiffre **n'est pas** une mesure de mémoire totale du noyau ni une preuve de gain.

### Mise en perspective avec l'audit multitouch déjà acquis

La comparaison textuelle sur les fichiers `drivers/input/touchscreen/zforce_i2c.c` de ce dépôt et de [giorgio130/linux-2.6.35-kobo-multitouch](https://github.com/giorgio130/linux-2.6.35-kobo-multitouch) montre **613 lignes de Marek sur 651** identiques à des lignes présentes chez Giorgio (≈94 %, y compris lignes répétées) ; les SHA des fichiers diffèrent, avec évolution des événements/erreurs tactiles. Cela indique **une base de code très proche, pas nécessairement une filiation Git démontrée**. Aucun avantage tactile supplémentaire pour PMKB n'est qualifié : la valeur **nouvelle** de cet audit est surtout la logique **EPDC CRC16 / buffers / framebuffer**.

## Décisions PMKB et critères de qualification

1. **RETENIR comme comparateur R1/PMKB-UI** : algorithme de tuiles CRC16, seuil de rafraîchissement complet et optimisation de buffers ; **ne pas intégrer le pilote complet**, ne pas toucher à l'image FIRST BOOT ou à son noyau.
2. **Prochain test hôte éventuel** : générer des images synthétiques **800×600 et 1440×1080**, plusieurs orientations, changements fins/gros aplats, lignes voisines des bords, et vérifier que l'heuristique ne manque aucune zone, n'accède pas hors bornes et maîtrise les appels `SEND_UPDATE`. Mettre en concurrence l'invalidation explicite de PMKB-UI (moins de CPU/veille). Aucun code de ce dépôt n'est nécessaire pour construire ces tests d'hypothèse.
3. **Mesure EPDC après FIRST BOOT physique** : RAM réservée réelle, nombre de buffers, cadence/latence de rafraîchissement, ghosting, CPU et impact énergétique. L'allocation de 15 Mo annoncée sur Touch ne prouve aucune économie sur Aura HD.
4. **Tactile** : garder le lot ZForce R1/R3 acquis, avec contrôles de validation de trames, ID, axes et `SYN_DROPPED` ; **pas de double import** de deux variantes proches.
5. **Licences** : noyau GPL et fichiers hétérogènes ; avant reprise d'un fragment, contrôler sa licence particulière et les obligations de diffusion des modifications. Aucun contenu GPL tiers incorporé ici.
